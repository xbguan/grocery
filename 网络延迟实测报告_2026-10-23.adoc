== 一句话结论

经本地中继 `127.0.0.1:7899`（→ 公司 3proxy `172.17.2.15:7887`）访问，三个站点 **90 次请求全部成功**，可用延迟为 *0.65 ~ 1.9 秒*；
而 **不经代理直连，三个站点 100% 超时**。你截图里那份报告的数据来自「绕过代理的直连」，因此不能代表日常速度。

== 为什么那份报告说「127.0.0.1:7899 无响应」

这句话的意思是：*跑测试的那个程序去连本机 7899 端口没连上，于是它放弃了代理，改成裸连测速。*

所以它后面的数字全是「没有代理」时的结果：

[cols="1,1,1",options="header"]
|===
|站点 |它给出的结果 |含义
|OpenAI |403，3.15 秒 |地区限制拒绝（不是延迟）
|Google |30/30 连接超时 |被墙，5 秒是它自己设的超时阈值
|YouTube |30/30 连接超时 |同上
|===

也就是说，**那份报告测的不是你的代理链路，而是断网状态。** 它自己也写了「以上数据来自绕过代理的直连请求」。

=== 它连不上 7899 的可能原因

. 那次测试是在 *ChatGPT 桌面版里的 Codex 面板* 跑的，它的命令执行环境是沙盒进程，不一定继承 `~/.codex/.env` 里的代理变量；一旦变量缺失，它就会退回直连。
. 它的 TCP 超时设在 5 秒，而中继收到请求后要先连公司 3proxy（8 秒超时上限）+ 做 Basic 认证；如果那一刻 VPN 抖动，5 秒内确实会「无响应」，它就会误判成代理坏了。
. 今天 19:25 才开机，19:41 测试时 VPN 链路刚建立不久，属于最容易抖动的时段。

=== 怎么当场验证

在任意终端（或让 Codex 执行）跑这一行，返回 `204` 就说明中继是活的：

[source,bash]
----
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' \
  -x http://127.0.0.1:7899 https://www.google.com/generate_204
----

== 测试方法

* 出口：`http://127.0.0.1:7899`（本地免认证中继 → 公司 3proxy）
* 样本：每站点 30 次，四站点交替执行（避免单站点扎堆造成偏差）
* 指标：完整 HTTPS 请求耗时（DNS + TCP + TLS + 首字节），非 ping
* 单请求超时：20 秒
* 时间：2026-10-23 19:5x（北京时间）

== 结果（经代理）

[cols="2,1,1,1,1,1,2",options="header"]
|===
|站点 |成功/总数 |均值 |中位数 |P95 |最慢 |状态码

|chatgpt.com/backend-api/me
|30/30 |0.727 s |0.689 s |1.054 s |1.148 s |401（未登录，正常）

|api.openai.com/v1/models
|12/30 |0.388 s |0.262 s |0.716 s |0.795 s |401 / 18 次连接被重置

|google.com/generate_204
|30/30 |0.651 s |0.645 s |0.736 s |0.779 s |204

|youtube.com
|30/30 |1.941 s |1.711 s |2.432 s |4.907 s |200
|===

=== 链路分段耗时（上游直连 3proxy）

[cols="2,1",options="header"]
|===
|环节 |耗时
|到 `172.17.2.15:7887` 的 TCP 握手 |0.014 ~ 0.020 s
|TLS 握手到目标站 |约 0.34 s
|完整请求（google 204） |约 0.65 s
|===

RTT 主要花在「公司出口 → 境外站点」这一段，本地中继只增加约 10 ~ 20 ms（对比直连 3proxy 的 0.64 s，经中继 0.65 ~ 0.69 s）。

== 直连对照（不走代理）

[cols="2,1,1",options="header"]
|===
|站点 |结果 |耗时
|api.openai.com |5/5 连接失败 |6.00 s（超时）
|google.com |5/5 连接失败 |6.00 s（超时）
|youtube.com |5/5 连接失败 |6.00 s（超时）
|===

这条对照说明：本机**必须**走代理，直连是 0 成功率。

== 解读

* **chatgpt.com 稳定**：30/30 通，中位 0.69 s。401 是因为没带登录凭据，属于预期响应，恰恰证明链路通到 OpenAI 了。
* **api.openai.com 不稳**：30 次里 18 次被重置（TLS reset）。这是公司出口对该域名的策略性拦截，不是本地配置问题；能通的 12 次中位仅 0.26 s。**Codex 走的是 chatgpt.com/backend-api，不受影响。**
* **youtube 看起来慢是页面重**：204 的 google 与 youtube 的 TLS 耗时接近，1.9 s 里大部分是首页 HTML 与资源首包的体积，不是链路延迟。
* **P95 与中位差距小**（除 youtube），说明链路抖动不大，没有明显长尾。

== 建议

. 用 `chatgpt.com`（Codex CLI 就走这条），不要依赖 `api.openai.com`，后者会被公司出口重置。
. 想让 ChatGPT 桌面版的 Codex 面板也稳定走代理，可在启动 App 前导出代理变量，或直接在面板里明确让它用 `-x http://127.0.0.1:7899`。
. 判断「是不是又变慢了」用上面那行 curl 做基线：0.6 ~ 0.8 s 属正常，持续 > 2 s 或返回非 2xx/401 才需要排查。
